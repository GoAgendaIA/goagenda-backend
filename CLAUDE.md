# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

GoAgenda backend: a FastAPI service that runs an AI-driven booking assistant for multiple businesses (salons, barbershops, spas, etc), exposed as a public, per-business web chat (`/chat/<business_id>/...`) that the business owner shares with their own clients as a unique link. The agent (`agent/`, built on LangGraph) handles the conversation: answering questions about services/hours, booking, cancelling, and rescheduling appointments, and handing off to a human on request. WhatsApp (either an official Meta Cloud API number, or an unofficial number via a separate Baileys microservice) is used only for outbound messages now — appointment reminders and auto-confirmation of web bookings — the conversational bot no longer runs over WhatsApp. A companion Flutter app (not in this repo) is the business owner's dashboard.

Data lives in Supabase (Postgres + Auth). There is no ORM — all queries go through the `supabase-py` client directly in `services/db.py` or inline in route files. The chat agent additionally talks to Postgres directly (not through the REST API) for its LangGraph checkpointer.

## Running locally

```bash
pip install -r requirements.txt
uvicorn main:app --reload
```

Requires a `.env` file (not committed) with at least: `SUPABASE_URL`, `SUPABASE_KEY`, `DATABASE_URL` (direct Postgres connection — see README for the Supabase pooler gotcha), `OPENAI_API_KEY`, `WHATSAPP_TOKEN`, `VERIFY_TOKEN`, `BAILEYS_SERVICE_URL`, `BAILEYS_INTERNAL_API_KEY`, and either `FIREBASE_CREDENTIALS_JSON` (production, JSON pasted as a string) or a local `firebase-credentials.json` file for push notifications. Importing `routes.chat_routes` (transitively, `agent/graph.py`) opens a Postgres connection pool and runs `PostgresSaver.setup()` at module import time, so the app fails fast on startup if `DATABASE_URL` is missing or unreachable.

## Tests

```bash
pip install -r requirements-dev.txt
pytest                 # todas las pruebas (~4 s)
pytest --cov           # con cobertura; falla si baja de 90% (.coveragerc)
pytest tests/test_tools.py -k zona   # un subconjunto
```

The local `.env` points at **production** (Supabase, OpenAI, WhatsApp, Wompi) and importing some modules has real side effects (`agent/graph.py` opens a Postgres pool; `main.py` seeds the super admin and starts the reminder scheduler). `tests/conftest.py` neutralizes all of that before any app code is imported: `load_dotenv` is disabled and every env var is fake, outbound sockets raise `RedBloqueadaEnPruebas` (a test missing a mock fails instead of reaching production), Supabase is an in-memory fake that really filters/projects (`tests/fakes.py:FakeSupabase` — seed with `db.sembrar(...)`, simulate outages with `db.fallar_en[tabla] = Exception(...)`, partial unique indexes with `db.agregar_unico(...)`), the LangGraph checkpointer is in-memory, and APScheduler is a no-op. Fixtures: `db` (autouse, reset per test), `cliente` (TestClient over the real `main.app`) and `como("user-id")` (Bearer headers resolved by the real auth dependency). Agent tests run the real graph with the LLM replaced by `tests/fakes.py:ModeloGuionado` (scripted `AIMessage`s). Never point tests at real services.

There is no linter or build step configured in this repo. This is a pure Python/FastAPI project — there is no Node.js code or tooling here. The Baileys WhatsApp connector (`@whiskeysockets/baileys`) is a separate Node service that lives outside this repo and is only ever talked to over HTTP via `BAILEYS_SERVICE_URL` (see `services/baileys_client.py`); do not add `package.json`/`node_modules` back to this repo for it.

To manually exercise the AI conversation flow, use the public chat endpoints directly (`routes/chat_routes.py`): `POST /chat/{business_id}/sessions` to get a `session_id`, then `POST /chat/{business_id}/sessions/{session_id}/messages`. No auth required — see the README's "Chat API" section for the full contract.

## Architecture

**The chat agent (`agent/`) is the core of the system**, built as a LangGraph `StateGraph`, and is the first place to look for booking/conversation behavior:
- `agent/state.py` — `AgentState`: `messages` (reducer `add_messages`), `business_id`, `client_phone`, `transferido`. `business_id` is set by the route handler on every turn from the trusted URL path param — it is never an LLM-controllable value, which is what makes tenant isolation hold even if the model hallucinates.
- `agent/tools.py` — every agent action is a `@tool`, no exceptions: `registrar_telefono_cliente`, `consultar_servicios_disponibles`, `consultar_horas_disponibles`, `crear_cita`, `consultar_citas_cliente`, `cancelar_cita`, `reprogramar_cita`, `transferir_a_equipo`. `business_id` and `client_phone` are injected into tools from graph state via `Annotated[str, InjectedState(...)]` rather than being LLM-supplied arguments. Client identity is phone-based, never a national ID: `registrar_telefono_cliente` is the *only* tool that sets `client_phone` (a `Command` state update), and the tools that need an identified client (`crear_cita`, `consultar_citas_cliente`, `cancelar_cita`, `reprogramar_cita`) read it from state and return a friendly error asking for the phone first if it isn't set yet.
- `agent/prompts.py` — `build_system_prompt` encodes most of the actual product behavior (timezone/format rules, confirmation-before-booking, anti-prompt-injection rules, tone per business type, no-wall-of-text formatting, the "ask for phone, never ID" identification rule). Changing bot behavior usually means editing this prompt, not the graph/tool Python code.
- `agent/graph.py` — wires the graph (`agent` node ⇄ `tools` node via `tools_condition`/`ToolNode`), builds the system prompt fresh every turn (so hour/service changes are picked up immediately), and owns the checkpointer: a `psycopg_pool.ConnectionPool` + `PostgresSaver` created once at import time (module-level singleton, same pattern as the `supabase` client in `services/db.py`). Exposes `enviar_mensaje(business_id, session_id, mensaje)` and `obtener_historial(business_id, session_id)`, used by `routes/chat_routes.py`. The LangGraph `thread_id` is always `f"{business_id}:{session_id}"` — this prefix is the actual isolation mechanism between businesses, independent of anything the URL router does.
- Availability/scheduling logic (`services/scheduling.py`: `generar_horas_disponibles`, `es_hora_valida`, `hay_choque_de_horario`, `formatear_fecha_natural`, `ahora_local`) is shared between the agent's tools and the manual booking endpoint (`routes/manual_appointments.py`) so both entry points enforce the same business hours, lunch break, and conflict rules. All times are naive `datetime`s assumed to be in `America/Bogota` (`TZ_NEGOCIO`) — the server itself runs in UTC (Railway), so `ahora_local()` exists specifically to avoid "today"/"tomorrow" being computed a day off after 7pm local time.
- Every model call's token usage is logged via `services/ai_usage_tracking.py:registrar_uso`, which also triggers a one-time-per-month push alert when a business crosses 80% of its configured `monthly_ai_budget_usd`.

**Chat endpoints** (`routes/chat_routes.py`) are intentionally public/unauthenticated — the per-business link itself is the access control, the same way the old self-service booking web worked. `GET /chat/{business_id}/config` lets a frontend check `enabled` (`plan != "none"`) before rendering the widget; `POST /chat/{business_id}/sessions` mints a `session_id`; the message and history endpoints do the actual conversing. See the README's "Chat API" section for exact request/response shapes and a `curl` walkthrough.

**WhatsApp is now outbound-only.** `POST /webhook` (Meta) and `POST /baileys/message` (`routes/baileys_routes.py`) still exist but no longer call into the agent — `webhook.py` keeps only Meta's verification handshake and the bridge that auto-confirms a pending web-booked appointment when the client replies with a fixed confirmation phrase; `baileys_routes.py`'s message endpoint is now a no-op (`{"respuesta_ia": null}`) kept only so the external Baileys microservice doesn't break if it still posts there. `services/reminder_service.py` picks Meta vs. Baileys per business (based on whether `whatsapp_phone_number_id` is set) purely for sending reminder texts.

**Client-facing WhatsApp notifications use a second, GoAgenda-owned number**, separate from the per-business `whatsapp_phone_number_id` above: `GOAGENDA_WHATSAPP_TOKEN`/`GOAGENDA_WHATSAPP_PHONE_NUMBER_ID` in `services/whatsapp.py` (`enviar_confirmacion_cita_cliente`), fired best-effort from `agent/tools.py:crear_cita` and `routes/manual_appointments.py:crear_cita_manual` whenever an appointment is created (both insert with `status="confirmed"` — see `services/db.py:create_appointment`). The chat agent's `registrar_telefono_cliente` tool (and `services/whatsapp.py:normalizar_numero_whatsapp`, which it now delegates to) requires and validates a real Colombian WhatsApp number instead of accepting any phone/landline string. Because clients never message this number first, `enviar_confirmacion_cita_cliente` sends an approved **message template** (`type: "template"`, `GOAGENDA_WHATSAPP_CONFIRMATION_TEMPLATE`/`_LANG`, default `confirmacion_cita_goagenda`/`es_CO`) rather than free text — a free-text attempt was confirmed in production to be accepted with HTTP 200 but then fail async via the status webhook with error `131047` ("Re-engagement message", outside the 24h session window). See the README's "Notificaciones de WhatsApp al cliente" section for the exact template body and how to change it (must be re-approved in Meta before the code's copy can change), and `POST /test-whatsapp-confirmation` (`main.py`) to test a real send once the template shows `APPROVED` in Meta Business Manager.

**Auth model** (`services/auth.py`): two independent mechanisms, not interchangeable, neither of which applies to the chat endpoints (those are public by design).
- End-user requests (from the Flutter app) carry a Supabase Auth JWT in `Authorization: Bearer <token>`, validated by `obtener_usuario_actual`. Ownership is then checked per-request with `verificar_dueno(business_id, user_id)` against the `businesses.owner_id` column — almost every business-scoped admin route depends on both.
- Server-to-server calls (the Baileys microservice calling back into this backend, plus internal/test endpoints) use a shared secret in the `x-api-key` header, validated by `requiere_api_key_interna` against `BAILEYS_INTERNAL_API_KEY`.

**Push notifications** (`services/push_notifications.py`) go through Firebase Cloud Messaging to the business owner's device (not the client), for events like new/cancelled/rescheduled appointments and budget alerts. Firebase Admin is a lazy singleton initialized from either `FIREBASE_CREDENTIALS_JSON` (prod) or a local `firebase-credentials.json` file.

**Realtime WebSocket** (`services/realtime.py`, `routes/realtime_routes.py`): `GET /ws/appointments?business_id=<id>` pushes an event to the Angular panel every time an appointment is created/updated/cancelled, regardless of origin (AI agent, manual panel booking, WhatsApp/Supabase webhook confirmation) — powers the header notification bell and the calendar's auto-refresh. See the README's "WebSocket de tiempo real" section for the full auth handshake and close-code contract. `GestorConexionesTiempoReal` keeps connections in an in-process dict keyed by `business_id`; the sync call sites (`agent/tools.py` tools, `manual_appointments.py`, `webhook.py` — none of them `async def`, so they can't `await`) call the sync `emitir_evento_cita(tipo, business_id, appointment_id)` helper, which re-reads the appointment with its joins and hands off to the event loop via `asyncio.run_coroutine_threadsafe` (the loop reference is captured once in `main.py`'s `startup` event). This in-memory connection map is per-process — it does not survive or sync across multiple backend instances/workers (see the README limitation note); fine for a single-instance deployment, but would need a shared pub/sub (Postgres `LISTEN/NOTIFY` or Redis) before scaling horizontally.

**Metrics center** (`services/metrics.py`, `routes/metrics_routes.py`, super admin only under `/admin/metrics/*`): computes global and per-business analytics in Python over the paginated appointment history, fed by instrumentation added in `metricas_analitica.sql` (`appointments.source` set at insert — `ai` from `finalizar_creacion_cita`/`crear_cita_pendiente_pago`, `manual` from `create_appointment`'s default — plus `cancelled_by`, reschedule counters maintained partly by a DB trigger, and the `chat_sessions` table written best-effort by `services/conversation_tracking.py`). Definitions and caveats are in `docs/METRICAS_ANALITICA.md`; the SQL must run before the code that inserts `source`.

**`businesses.plan` gates whether the chat agent runs at all**: `"none"` disables it entirely (`GET /chat/{business_id}/config` reports `enabled: false`, and the message endpoint replies with a fixed "not available" message instead of invoking the LLM); any other value (including `"basic"`) runs the full conversational flow — there is no more plan-based redirect to an external booking web.

**Reminders** run on an in-process `APScheduler` `BackgroundScheduler` started in `main.py` (5-minute interval, not a separate worker process), calling `services/reminder_service.py:revisar_y_enviar_recordatorios`. Each business configures its own `reminder_hours_before` lead time.

## Conventions

- Function/variable names, docstrings, and print statements are in Spanish throughout the codebase (domain language: `cita` = appointment, `negocio` = business, `horario` = hours, `recordatorio` = reminder); comments explain *why*, matching the existing style — follow this rather than switching to English.
- Route modules follow a flat pattern: one `APIRouter()` per resource in `routes/`, registered directly in `main.py`, with Pydantic models defined inline in the route file rather than in a shared schemas module.
- `agent/` and `core/` are intentionally flat, single-purpose packages (not `agents/<name>/`, not a generic `repositories/` layer) — this codebase deliberately avoids adding structure beyond what's needed; most of `services/db.py`, `services/auth.py`, and the non-chat route files were left untouched during the LangGraph migration rather than folded into new layers.
- Deletion is soft where it would otherwise break referential history (e.g. `services` are marked `active: False` rather than removed, since existing appointments reference them).
- New Supabase tables/migrations in this repo are checked in as standalone `.sql` files at the repo root (see `excluded_chats.sql`) meant to be run manually via the Supabase SQL editor — there's no migration framework.
